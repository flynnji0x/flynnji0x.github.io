# 从0开始学架构（二）

### 22 CAP理论

- 对于设计分布式系统的架构师来说，CAP是必须掌握的理论
- 版本1：对于一个分布式计算系统，不可能同时满足一致性（Consistence），可用性（Availability），分区容错性（Partition Tolerance）三个设计约束
- 版本2：再一个分布式系统（指互相连接并共享数据的节点的集合）中，当涉及读写操作时，只能保证一致性（Consistence），可用性（Availability），分区容错性（Partition Tolerance）三者中的两个，另外一个必须被牺牲
- 分布式系统不一定会互联和共享数据
    - Memcache集群，不互联和共享数据
    - MySQL集群，会互联和共享数据
- CAP关注的是对数据的读写操作，而不是分布式系统的所有功能
- 解释
    - 一致性
        - 对某个指定的客户端来说，读操作保证能够返回最新的写操作结果
    - 可用性
        - 非故障的节点再合理的时间内返回合理的响应（不是错误是超时的响应）
    - 分区容错性
        - 当出现网络分区后，系统能够继续”履行职责“
- CAP应用
    - 分布式系统理论上不可能选择CA架构，只能选择CP或者AP架构
    - 为什么必须选择P，因为网络本身无法做到100%可靠，所以分区容错是必然的，而C和A是相互冲突的
### 23 CAP理论细节

- 细节点
    - CAP关注的粒度是数据，而不是整个系统
    - CAP是忽略网络延迟的，但实际情况下，网络延迟是客观存在无法避免的
    - 正常运行情况下，不存在CP和CA的选择，可以同时满足CA
    - 架构设计时，既要考虑分区发生时选择CP还是AP，也要考虑分区没有发生时如何保证CA
- ACID
    - ACID关注的是数据库事务，而CAP关注的是分布式数据读写
    - 定义
        - 原子性
        - 一致性
        - 隔离性
        - 持久性
- BASE
    - 核心思想是即使无法做到强一致性，但应用可以采用适合的方式达到最终一致性
    - 定义
        - 基本可用，Basically Available
            - 分布式系统再出现故障时，允许损失部分可用性，即保证核心可用
        - 软状态，Soft State
            - 允许系统存在中间状态，而该中间状态不会影响系统整体可用性
        - 最终一致性，Eventual Consistency
            - 系统中的所有数据副本经过一定时间后，最终能够达到一致的状态
    - BASE理论本质上是对CAP的延伸和补充，更具体地说，是对CAP中AP方案的一个补充
- ACID是数据库事务完整性的理论，CAP是分布式系统设计理论，BASE是CAP理论中AO方案的延伸
### 24 FMEA方法，排除架构可用性隐患的利器

- FMEA，Failure mode and effects analysis，故障模式与影响分析
- 在架构设计领域，FMEA的具体分析方法是：
    - 给出初始的架构设计图
    - 假设架构中某个部件发生故障
    - 分析此故障对系统功能造成的影响
    - 根据分析结果，判断架构是否需要继续优化
- FMEA分析表
    - 功能点
    - 故障模式
    - 故障影响
    - 影响严重程度
    - 故障原因
    - 故障概率
    - 风险程度
    - 已有措施
    - 规避措施
    - 解决措施
    - 后续规划
### 25 高可用存储架构：双机架构

- 存储高可用的复杂性主要体现在如何应对复制延迟和中断导致的数据不一致问题
- 常见的双机高可用架构
    - 主备复制
        - 架构简单，对于主机和备机只需要进行数据复制即可，无须进行状态判断和主备切换这类复杂的操作
        - 备机仅仅只为备份，没有提供读写操作，硬件成本有浪费
        - 需要人工干预，无法自动恢复
    - 主从复制
        - 在主机故障时，读操作相关的业务可以继续运行
        - 从机提供读操作，发挥了硬件的性能
        - 客户端需要感知主从关系，并将不同的操作发给不同的机器处理
    - 双机切换
        - 切换方案，需要考虑的几个关键设计点：
            - 主备间的状态判断
                - 状态传递的渠道
                - 状态检测的内容
            - 切换的决策
                - 切换时机
                - 切换策略
                - 自动程度
            - 数据冲突解决
                - 当原有故障的主机恢复后，新旧主机之间可能存在数据冲突
        - 常见的架构
            - 互连式
                - 主备机直接建立状态传递的渠道
                - 如果状态传递的通道本身有故障，那备机认为主机发生故障而升为主机，导致最终出现两个主机
            - 中介式
                - 在主备两者之外引入第三方中介，主备机之间不直接连接，通过中介来传递状态信息
                - 连接管理更简单
                - 状态决策更简单
                - zookeeper，实现了高可用集群架构，解决了中介本身的可靠性问题
            - 模拟式
                - 主备机之间不传递状态信息，而是备机模拟成为一个客户端，通过请求主机，根据响应来判断主机的状态
                - 模拟式读写操作获取的状态信息只有响应信息，没有互连式那样有多种状态，基于有限的状态来做状态决策，可能出现决策偏差
    - 主主复制
        - 两台机器都是主机，互相将数据复制给对方，客户端挑选任意一台机器进行读写操作
        - 采用主主复制架构，必须保证数据能够双向复制，而很多数据是不能双向复制的
        - 所以一般适用于临时性，可丢失，可覆盖的数据场景
### 26 高可用存储架构：集群和分区

- 数据集群
    - 数据集中集群
        - 复杂度
            - 主机如何将数据复制给备机
            - 备机如何检测主机状态
            - 主机故障后，如何决定新的主机
    - 以zookeeper为典型，通过ZAB算法来解决上述的问题
    - 数据分散集群
        - 复杂度体现在如何将数据分配到不同的服务器上，考虑的设计点：
            - 均衡性
            - 容错性
            - 可伸缩性
        - Hadoop，Elasticsearch
- 数据分区
    - 数据分区是指将数据按照一定的规则进行分区，不同分区发布在不同的地理位置上，每个分区存储一部分数据，通过这种方式来规避地理级别的故障所造成的巨大影响
    - 几个需要考虑的方面
        - 数据量
            - 数据量越大，分区规则越复杂，考虑的情况也越多
        - 分区规则
        - 复制规则
            - 集中式
            - 互备式
            - 独立式
### 27 如何设计计算高可用架构？

- 计算高可用的设计复杂度主要体现在任务管理方面
- 计算高可用架构设计的关键点有：
    - 哪些服务器可以执行任务
        - 每个服务器都可以执行任务
        - 只有特定服务器能执行任务，例如zookeeper的Leader才能处理写操作请求
    - 任务如何重新执行
        - 第一种策略，已经分配的任务即使执行失败也不做任何处理
        - 第二种策略，设计一个任务管理器来管理需要执行的计算任务
- 常见的计算高可用架构
    - 主备
        - 主备架构又细分为冷备架构和温备架构
        - 冷备
            - 程序包和配置文件都准备好，但业务系统没有启动
        - 温备
            - 备机上的业务系统已经启动，至少不对外提供服务，一般情况下推荐用温备的方式
    - 主从
        - 主从架构的从机也执行任务，发挥了从机的硬件性能
        - 主从架构需要将任务分类，任务分配器会复杂一些
    - 集群
        - 集群方案根据集群种节点角色的不同，分为两类
            - 对称集群
                - 也叫负载均衡集群
                - 每个服务器的角色都一样，可以执行所有任务
                - 设计关键点在于两点：
                    - 任务分配器需要选取分配策略
                        - 轮询或者随机
                    - 任务分配器需要检测服务器状态
                        - 常用做法是任务分配器和服务器之间通过心跳来传递信息
            - 非对称集群
                - 集群种的服务器分为多个不同的角色，不同角色执行不同的任务，例如Master-Slave角色
                - 集群会通过某种方式来区分不同服务器的角色
                    - zookeeper的ZAB算法选举出Master服务器
                    - 或者简单取存活服务器节点ID最小的服务器作为Master服务器
                - 相比负载均衡集群
                    - 任务分配策略更加复杂
                        - 需要将任务划分为不同类型并分配给不同角色的集群节点
                    - 角色分配策略实现比较复杂
                        - 用ZAB，Raft这类算法实现Leader的选举
### 28 业务高可用的保障：异地多活架构
        - 根据地理位置上的距离来划分，异地多活架构可以分为
            - 同城异区
                - 结合复杂度，成本，故障发生概率来综合考虑，同城异区是应对机房级别故障的最优架构
            - 跨城异地
                - 因为距离较远，导致的架构复杂度大大上升
            - 跨国异地

### 32 可扩展架构的基本思想和模式
        - 可扩展的基本思想
            - 将原本大一统的系统拆分为多个规模小的部分，扩展时只修改其中一部分即可，降低改动风险
        - 常见的拆分思路
            - 面向流程拆分
                - 将业务流程拆分为几个阶段，每个阶段为一部分
            - 面向服务拆分
                - 将系统提供的服务拆分，每个服务作为一部分
            - 面向功能拆分
                - 将系统提供的功能拆分，每个功能作为一部分
### 33 分层架构和SOA
        - 分层架构
            - C/S架构，B/S架构
            - MVC架构，MVP架构
            - 逻辑分层架构
            - 核心在于，需要保证各层之间的差异足够清晰，边界足够明显，让人看到架构图后就能看懂整个架构
            - 特点
                - 好处在于强制将分层依赖限定为两两依赖，降低整体系统的复杂度
                - 典型的缺点就是性能，每一此业务请求都需要穿越所有的架构分层，多少有一些性能的浪费
        - SOA
            - 全称是，Service Oriented Architecture，即面向服务的架构
            - 为了应对传统IT系统的问题，SOA提出了3个关键概念
                - 服务
                    - 所有的业务功能都是一个服务，服务可大可小，可简单可复杂
                - ESB
                    - Enterprise Service Bus，企业服务总线
                - 松耦合
                    - 目的是减少服务间的依赖和互相影响
### 34 微服务架构
        - SOA和微服务架构本质上是两种不同的架构设计理念，只是在“服务”这个点上有交集而已
        - 微服务的三个关键词
            - small
            - lightweight
            - automated
        - 微服务的坑
            - 服务划分过细，服务间关系复杂
                - 单个服务的复杂度下降，但服务间的复杂度却上升了，因为微服务将系统内的复杂度转移为服务间的复杂度了
            - 服务数量太多，团队效率急剧下降
            - 调用链太长，性能下降
            - 调用链太长，问题定位困难
            - 没有自动化支撑，无法快速交付
            - 没有服务治理，微服务数量多了后管理混乱
### 35 微服务架构最佳实践-方法篇
    - 康威定理
    - 服务粒度
        - 建议按团队规模进行拆分，三个火枪手原则，即一个微服务三个人负责开发
    - 拆分方法
        - 基于业务逻辑拆分
        - 基于可扩展拆分
            - 将已经成熟和改动不大的服务拆分为稳定服务
            - 将经常变化和迭代的服务拆分为变动服务
        - 基于可靠性拆分
            - 避免非核心服务故障影响核心服务
            - 核心服务高可用方案可以更简单
            - 能够降低高可用成本
        - 基于性能拆分
    - 基础设施
        - 实际上真正决定微服务成败的，是被大部分人忽略的“automated”
        - 基础设施优先级
            - 1，服务发现，服务路由，服务容错，基本的微服务基础设施
            - 2，接口框架，API网关，主要是为了提升开发效率，接口框架是提升内部服务的开发效率，API 网关是为了提升与外部服务对接的效率
            - 3，自动化部署，自动化测试，配置中心，主要是为了提升测试和运维效率
            - 4，服务监控，服务跟踪，服务安全，主要是为了进一步提升运维效率
