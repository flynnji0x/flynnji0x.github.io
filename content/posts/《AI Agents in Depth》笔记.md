## Agent 的本质

现代 Agent 系统的本质可以用一个简洁的公式来表达：

```
Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具
```

换一种更直观的说法：**Agent = 大脑 + 眼睛 + 手脚**。大脑负责思考和决策，眼睛提供思考所需的全部信息，手脚将决策转化为对现实世界的改变。

### LLM：决策核心

大语言模型（Large Language Model, LLM）是 Agent 的决策核心，其能力体现在：

- 零样本泛化（Zero-shot Generalization）：即使面对从未见过的任务，LLM Agent 也能通过组合已有知识来处理，无需任何示例。
- 少样本适应（Few-shot Adaptation）：只需在提示中给出两三个示范例子，模型就能掌握一种新的任务模式。

## ReAct 模式

Agent 执行任务的核心模式叫做 ReAct（Reasoning + Acting）。

Agent 的核心工作原理——LLM 通过 ReAct 循环，在上下文的辅助下使用工具完成任务。

## Model + Harness

Harness 的核心就是原公式中的"上下文 + 工具"，再加上三层保障机制：

- 约束（Constraint）：限定 Agent 能做什么、不能做什么
- 验证（Verification）：检查 Agent 做得对不对
- 纠正（Correction）：做错了怎么补救

```
Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正] = Model + Harness
```

根据 Anthropic 的经验，成功的 Agent 系统遵循三个核心原则。

另外，在工程实现上：清晰的代码优于聪明的抽象。

## 上下文：Agent 能力的真正上限

代码、流程、环境这三类信息——构成了 Agent 有效工作的最低信息需求。模型本身的智力只是基础，上下文的质量才是 Agent 能力的真正上限。

模型的长思维链能力和工具调用能力都对上下文学习（In-Context Learning）能力有很强的依赖。

## Agent Skills

Agent Skills 的核心思想是将 Agent 的能力模块化为独立的、可按需加载的知识包。每个 Skill 本质上是一套包含专业领域指导的提示词集合。

Skill 内容放在上下文的什么位置？这是一个根本性的设计决策，直接关系到 KV Cache 效率和模型的指令遵循效果。

## Agent 状态栏

基于上述的理论基础，Agent 状态栏包括以下几种类型的信息：

- 任务规划
- 事件的侧信道信息（Side-channel Information）
- 环境的当前状态
- 可用能力清单

### 五种状态栏技术

agent-status-bar 实验框架实现了五种状态栏技术，每种都可以独立启用或禁用：

1. 时间戳跟踪
2. 工具调用计数器
3. TODO 列表管理
4. 系统状态感知

这些技术协同工作会产生涌现效应（即单独使用时效果有限，组合起来却能产生超出预期的效果）。时间戳和工具计数器的结合使 Agent 能够理解操作的频率和时间分布；TODO 列表和系统状态的结合使 Agent 能根据环境调整任务策略；详细错误信息和工具计数器的结合使 Agent 在多次失败后不仅能改变策略，还能理解失败的原因。完全启用这些技术的 Agent 不再是机械执行指令的工具，而更像是一个有自我意识的助手——遇到文件不存在时先检查目录，再列出可用的文件，仍然找不到就在 TODO 中标记 cancelled 并添加替代任务。这种自适应的行为是单独的某一项技术无法实现的。

## 上下文压缩与腐化

### 压缩的两个动机

压缩上下文有两个截然不同的动机，理解这一点对设计压缩策略至关重要：

1. 第一，解决长度约束和成本约束。
2. 第二，提升思考质量——总结后的知识比原始形式更利于模型使用。

注意力机制的本质：上下文学习的内部机制更像检索而非推理。

### 上下文腐化（Context Rot）

长上下文会导致检索精度的下降。明明上下文窗口还远没有满，但 Agent 突然找不到关键信息了，或者反复纠结于一个早已解决的问题——这种现象被称为上下文腐化（Context Rot）。

以 Claude Code 的做法为参照，一个成熟的上下文管理系统通常包含五个层次。

## 记忆系统

### 记忆存储的选择

实践中的选择标准是：关键且少量的数据（如用户偏好、关键人物关系）用 Advanced JSON Cards 以保证可检索性；大量且非关键的对话事实用 Simple Notes 以降低成本；多数生产系统采用混合模式——同一 Agent 内不同类信息走不同路径。

### 用户记忆的隐私挑战

在构建用户记忆系统时，核心挑战是让 Agent 既能利用用户信息提供个性化服务，又不让敏感数据暴露在 LLM 上下文和系统日志中。

### 记忆压缩策略

实践中可以采用多层次的记忆压缩策略。第一层通过重要性评分筛选。一种常见的重要性评分思路是综合四个因素：

- 访问频率：经常被检索的记忆更重要
- 时间衰减：越久远的记忆越容易被遗忘
- 情感强度：带有强烈情感标记的记忆更易保留
- 信息独特性：重复信息的重要性降低

低于阈值的记忆标记为可压缩或可删除。

### 共享知识库与 RAG

构建共享知识库的核心技术是检索增强生成（Retrieval-Augmented Generation, RAG）。其核心思想是将大型语言模型的思考和生成能力，与外部知识库的广度和时效性相结合——模型本身的训练数据有截止日期，而知识库可以随时更新。

## Coding Agent

以开放任务为目标的通用 Agent，其核心是一个 Coding Agent（能自主编写、修改和执行代码的 Agent）加上文件系统。

代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力。

Coding Agent 加上文件系统，是开放任务型通用 Agent 最核心的技术基础。

### 七个核心工具

一个基础的 Coding Agent 只需配备以下七个核心工具：

1. Code Interpreter（代码解释器）：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码在其中运行即使出错也不会影响宿主机），安全执行 Python 代码
2. Bash Shell（命令行终端）：在终端中执行命令，如运行测试用例、处理特殊格式文件
3. 读文件工具：读取代码、配置、文档、日志等
4. 写文件工具：创建新文件或完全重写现有文件
5. 编辑文件工具：对现有文件进行局部修改，是代码维护和迭代的核心操作
6. 搜索文件名工具（Glob）：通过模式匹配快速定位文件系统中的目标文件，例如用 **/*.py 找出项目中所有 Python 文件
7. 搜索文件内容工具（Grep）：在文件内容中搜索特定的文本模式，例如搜索所有调用了某个函数的代码行

### 智能基座

大模型已经成熟到足以充当一种新的"智能基座"——类似传统操作系统屏蔽硬件、为上层应用提供统一抽象，大模型屏蔽了语言理解与思考规划的复杂性，为上层 Agent 提供统一的智能抽象。

### 架构原则

一条重要的架构原则：当写代码的和跑代码的都可能不可信时，真正可靠的约束不能待在被生成的代码里，而要待在它下面那层人类审查过的地基里。

### 五个实现技巧

并行与流式、上下文管理、环境感知、状态持久化、即时反馈——这五个实现技巧共同构成了高效 Coding Agent 的技术基础。它们不是孤立的优化点，而是相互配合的设计决策，共同指向一个目标：让 Agent 能够像经验丰富的开发者那样流畅地工作。

### 双 Agent 分工

采用双 Agent 分工而非单 Agent 循环的核心优势在于上下文管理。

## AI-ready 与软件工程

评估一个团队的"AI-ready"程度，一个简单的代理指标是：一个远程新人只靠代码仓库和文档，能不能独立开展工作。

软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化。

## 为什么编程是 AI 最强的领域

持这种看法的人（不乏 OpenAI、Anthropic 的研究者）会指出，AI 今天唯独在编程上最强，并不是因为代码对模型有什么特殊，而是因为编程是人类最开放的领域：海量开源代码摆在那里，可供学习；而绝大多数行业压根没有公开的信息与数据。
